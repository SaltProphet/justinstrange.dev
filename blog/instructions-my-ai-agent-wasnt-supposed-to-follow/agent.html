When a Webpage Talks Back

You give an AI agent a task, point it at the web, and wait for it to come back with an answer. Somewhere along the way, one of the websites it visits tries to give your agent instructions of its own. You don't see those instructions on the page. Unless the agent happens to mention them, you may never know they were there.

I started pulling on this thread after a routine browsing task: having my agent update my LinkedIn profile. Instead of just finishing the job, my agent stopped and reported that a webpage it visited contained suspicious hidden instructions written to direct automated systems reading the site.

Naturally, I went looking for them. I opened the same URLs in my browser, read through the visible pages, and popped open the raw HTML source to search for the phrasing the agent had described.

Nothing. Every page looked completely ordinary.

Why "View Source" Misses What Agents Read

If you've worked with web scraping or browser automation, you already know why "View Source" is a terrible witness. When a person looks at a webpage, the browser paints a visual layout filtered by CSS rules and screen dimensions. When a browser-based AI agent reads that same page, it usually ingests the live Document Object Model (DOM), accessibility trees, or raw textContent extractions.

Those two views don't have to match, and the raw HTML file you download manually isn't necessarily what the agent saw five minutes earlier. A server can inspect request headers—like User-Agent strings or sec-ch-ua browser client hints—and hand one page to Chrome while serving something else entirely to an automated client. Or the static HTML can arrive completely clean, only for JavaScript to decode a payload at runtime and inject it into an off-screen DOM node after the page finishes loading.

Because I couldn't reproduce the text from that first run, I treat the original incident as unverified and don't attribute it to a specific website. Still, not knowing whether the page had changed or what my agent had actually ingested bothered me enough that I built a tool to look directly at the gap between human viewports and agent inputs.

Building Hollowtext—and Avoiding False Positives

I called the tool Hollowtext (check.ps1, paired with a headless browser renderer and a local dashboard launched via npm run ui with a bookmarklet). Given a URL, it fetches the page as both an AI agent (User-Agent: GPTBot/1.0 (+https://openai.com/gptbot)) and a standard browser, checks subresources for runtime decode primitives and invisible Unicode characters, and renders the live DOM to compare what a human sees on screen against concealed nodes sitting in the page structure.

Building a scanner like this teaches you pretty quickly how easy it is to fool yourself. The web is full of hidden text that has nothing to do with manipulating AI: screen-reader aria-label and alt attributes, collapsed menus, and data: URI blobs. Even worse, if you point an agent User-Agent at a commercial site, there's a good chance Cloudflare steps in with a 403 bot-challenge page while your normal browser gets a 200 login screen. Compare those two responses naively and you get 0% text similarity—which looks like red-handed cloaking until you realize you're just comparing a security gate to a front door.

To keep Hollowtext honest, every check resolves to one of three states: SIGNAL, CLEAN, or BLOCKED. When an agent request hits a 403, 429, or 503 bot challenge, the tool marks the comparison BLOCKED (inconclusive, exit code 3) rather than crying wolf, and it ignores non-instruction noise like base64 strings inside data: URIs.

Controlled Fixture Verification (http://127.0.0.1:8731)

With that filtering in place, I ran Hollowtext against a controlled local test fixture (http://127.0.0.1:8731) across four routes (/static, /chcloak, /runtime, and /blocked) to verify how hidden instructions behave in the DOM and what the detector catches:

Figure 1 — Static concealment: To a person in a browser, the /static route is a dry, 362-character "Quarterly logistics update". In the live DOM that the agent receives, there are 559 characters spread across eight concealed nodes—text colored to match the background, display:none containers, CSS ::before generated content, and HTML attributes (alt, data-instructions, aria-label)—along with five invisible Unicode carrier characters that decode to "EXFIL".

Figure 2 — Client-hint cloaking: On /chcloak, the server keys on sec-ch-ua headers. Open it in standard Chrome and the page is clean. Fetch it as a non-browser client and the server slips in an off-screen (-9999,0) instruction node and a hidden canary (CANARY:d4c1).

Figure 3 — Runtime assembly: View the raw HTML source on /runtime and there isn't a single word of instruction text in the file. Once the page loads in the headless browser, JavaScript decodes a payload and drops it into an off-screen DOM node (-9999,-9999), expanding 362 visible characters into 866 characters of DOM text.

Route 4 — Bot-challenge gating (/blocked): Confirms that perimeter anti-bot challenges land in BLOCKED instead of generating false cloaking alerts.
